# RC4 original release authorization and public integrity inspection

This is source tooling for an exact `0.5.4rc4` Linux x64 candidate. The earlier
`0.5.4rc4.dev0` proposal could not pass the original qualification. Current
`0.5.4rc4` source still requires fresh successful installed qualification; this
change does not build, install, tag or publish a candidate. Synthetic unit controls
exercise orchestration and byte integrity; they are not installed proof.

Three operations have different authority:

| Operation | Required input | Result |
| --- | --- | --- |
| `prepare_original` | Original closed evidence trees and independent final pins | Reruns actual original-tree semantic gates, then stages exactly eight assets in a new directory. |
| `inspect_public` | Exported stage, externally pinned manifest SHA-256 and independent final product/source pins | Checks finite exported bytes and identities. `historical_semantic_replay`, `new_installed_execution` and `release_authorized` are all false. |
| `authorize_original` | The pinned stage, original closed evidence trees and the same independent final pins | Rechecks staged bytes, reruns original semantic gates, compares every retained original role and rechecks staged bytes again. |

Only `authorize_original` can feed RC4 tag authorization. Public inspection and
saved admission booleans cannot substitute. No verifier module, callback or
command is selected by a receipt. The fixed trusted verifier source must match
the complete bare final Git archive, including its independently pinned tool
manifest. Extra source files, caches, links and special entries refuse. The
original gate trees stay unchanged; inputs and previous refusal evidence are never
rewritten by staging. Failed temporary stages retain their complete unpublished
bytes and the original exception; they never become a final stage automatically.

## Original inputs

The externally hashed `sinter-original-rc4-context/v1` document supplies absolute
original labels for `repository`, `candidate`, `independent_review`, `workflow`,
`recovery`, `native`, `replacement`, `priors`, `replacement_owned_root`,
`replacement_candidate`, `replacement_repository` and `chromium`. Paths are
explicit operator inputs, not discovered from public receipts. The current trusted
source tree and all replacement paths must fit the existing strict replacement
owner's private-root rules. A separately archived bare final source tree is used
for trusted QA execution; a development checkout or a receipt-selected module is
not an alternative.

The context's `candidate` retains the four product files, actual Linux package
receipt and full dependency notices. `replacement_candidate` is a separate mount
with exactly the same DEB and package receipt bytes. Each gate has its own actual
original proof root. The complete trees, including empty directories, are captured
before semantic verification and compared again afterward. Actual executable gate
source copies are checked before any baseline verifier subprocess can run.

The externally hashed `sinter-original-rc4-trusted-pins/v1` document supplies the
full final `source_commit`, `source_archive_sha256`, `tool_manifest_sha256`,
`installer_sha256`, `package_receipt_sha256`, `native_archive_sha256`,
`portable_sha256`, `native_binary_sha256`, `independent_review_sha256`,
`chromium_sha256` and immutable `image_id`. There is no identity inferred from a
successful receipt. The source ZIP is independently re-created by the original
Git repository; the portable app and actual native payload are checked against it.

Original qualification invokes:

- Existing `_source`, `_native_payload` and `verify_target_receipt`, complete
  actual dependency/notice bytes and the preserved no-readline terminal-library
  notice policy.
- The independently pinned four-file final artifact/clean-install review. Its
  exact RC4 checks and complete raw clean receipt/context/log identities must
  match the installed package receipt and the same final source/package/binary.
- Fixed `rc4_installed_workflow_contract.verify_original`: the exact source-declared
  53-entry legacy or recognized 54-entry funding-enabled catalogue, 22 named UI
  checks, 13 roles and both actual app lifetimes. The complete installed CLI
  catalogue retains the exact source IDs and all definition fields. The actual
  count is recorded in workflow evidence and staged release notes; this does not
  claim that every catalogue operation was executed through the UI.
- Fixed `rc4_installed_recovery.verify`: both profiles, ten actual installed
  lifetimes and final candidate identity.
- Fixed `rc4_native_handoff_contract.verify`: the original four-entry baseline
  and separate fifth browser-handoff lifetime.
- Fixed `rc4_replacement_contract.verify`: the unchanged exact four-prior map,
  including published RC3 E, one final package and all original source/data/owner
  lifetimes. RC1–RC3 prior maps and release rules stay unchanged.
- Required native browser v3 and replacement v2 before/after host observations,
  including the actual original Docker, Chromium, Python and bundled Playwright
  Node identities. Native v3 also requires the owned short temporary directory's
  identity and completed removal.

The authorizer derives the expected catalogue count through the fixed trusted
`installed_workflow_qualification.source_operations` parser after checking the
complete pinned source/tool identity. It admits only that parser's closed 53/54
profiles, including the exact local funding extension in the 54-entry profile.
A 54-entry source cannot be labelled or authorized as 53. The RC4 independent
review uses the source-catalogue check name rather than claiming 53 UI executions.
Public integrity inspection derives the release-note count from the pinned source
ZIP as data; it never imports exported code or executes catalogue operations.
RC1–RC3 policies, prior maps, schema names and finite byte bounds are unchanged.

Missing adapters, missing raw files, another version/package/tool identity,
interrupted or failed cleanup and different final bytes refuse. This operation
revalidates the actual earlier runs; it does not claim to launch a new installed
run. A new independent clean install still has to be carried out and reviewed for
the final artifact before preparation can succeed.

## Export and public inspection

The exact eight upload assets remain:

1. `Sinter-0.5.4rc4-linux-x64.deb`
2. `Sinter-0.5.4rc4-linux-x64.tar.gz`
3. `sinter-0.5.4rc4-source.zip`
4. `sinter-0.5.4rc4.pyz`
5. `sinter-0.5.4rc4-qualification.zip`
6. `RELEASE-NOTES.md`
7. `candidate-release-manifest.json`
8. `SHA256SUMS.txt`

The qualification ZIP has one fixed `catalog.json` and deduplicated content-addressed
`blobs/` members. It retains the final actual proof trees, actual product/receipt
and notices, independent clean-install review, exact original closed inventories
and original semantic results. It does not collect all old source-review trees.
The reviewed catalog module is used only for its strict finite transport schema.
The same 64 MiB member and 256 MiB expanded bundle limits remain in force.
The uploaded encoded qualification ZIP has a separate 256 MiB bound; the old
policy did not apply the 64 MiB expanded-member limit to that outer container.
Actual final inventory and size measurements are required; fit is not preclaimed.
a complete original export that exceeds those limits refuses instead of dropping
roles or increasing a cap.

External host executables, Playwright libraries and the Docker daemon remain a
stated trust boundary. Their independently observed before/after fingerprint
records are retained, but Docker/Python/Chromium/Playwright Node executable bytes
are forbidden in the exported catalog. Product native runtime and notices remain
retained actual product inputs. Original labels are opaque public data; public
inspection never opens them, executes commands, imports exported code or writes
files. A source archive and arbitrary self-resealed receipts cannot authorize
publication.

Public inspection checks the exact externally pinned manifest, asset inventory,
SHA256SUMS, finite expanded ZIP inventory, every complete raw blob, product copies,
independent review and package receipt pins, final source version/commit/tool
manifest, portable source bytes and native archive binary identity. It never
claims that public integrity proves semantic qualification or compute/AI quality.
Full relocated historical semantic replay is optional future work, explicitly
false in this release policy.

## Stage and tag dispatch

`candidate_release.prepare`, `verify_plan` and publication-command rendering have
an exact RC4 branch before the old policy rejects RC4. Legacy versions retain their
existing policy and defaults. The original context/pins and independent file hashes
are mandatory for RC4 command-line staging or verification. Direct Python callers
must supply the typed trusted context/pins, and authorization requires the external
manifest SHA-256. The standalone tool exposes `prepare-original`, `inspect-public`
and `authorize-original` as separate commands; its help lists their exact inputs.

Shared verification, `verify`/`commands` CLI discovery and the tag identity gate
use one bounded discovery reader. An exact top-level RC4 schema, version, tag,
source identity and narrower Linux-only claim profile select the fixed original
authorizer. Nested version strings, duplicate JSON keys, missing/contradictory
profile fields and malformed UTF-8 refuse. Discovery itself grants no authority:
the externally pinned manifest and complete original semantic gates are still
independently rechecked. A finite RC4 manifest can use the unchanged 64 MiB member
bound; there is no arbitrary record-count cap. Every non-RC4 document still passes
through the unchanged legacy reader's 2 MiB limit and original version policy.
The 256 MiB expanded bundle and separately encoded ZIP bounds remain unchanged.

When discovery fails, descriptor cleanup preserves the identical first exception
object. Later cleanup exceptions, including interruptions, remain in its ordered
`manifest_cleanup_errors` tuple; `manifest_cleanup_error` retains the latest one
for existing callers. A `KeyboardInterrupt` that is the first fault still
propagates, whether it occurs during reading or the normal descriptor close.

`release_tag` requires the original context/pins and their hashes plus the external
manifest hash. It runs original authorization before the tag lookup and again
immediately before the sole atomic tag-creation POST. A refusal prevents that
POST. Existing or conflicting tags are never moved; old release assets are not
retagged or replaced. This source change does not modify release workflows and
cannot make a development CI publication no-op into a published candidate.

Only the installed Linux x64 scope can qualify. Other platforms, ordinary customer
browser download delivery, customer-device acceptance, physical customer menu
launch and general/live AI quality remain unsupported claims. Packages remain
unsigned and not notarised; users must never disable operating-system security.
The product stays local-first and useful offline for one trusted user. No hosted
collaboration, CRM, autonomous sender or automatic grant submission is added.
